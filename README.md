# 影像管家 · MediaCurator

macOS 原生照片 / 视频整理工具。面向「几万到几十万个文件」的本地媒体库，做四件事：

1. **查重** —— 精确重复（逐字节）+ 相似图片 + 相似视频
2. **批量重命名** —— 按拍摄时间、设备、序号等变量组合命名
3. **按条件归档** —— 依据拍摄时间、设备、类型等自动分级到对应目录
4. **可回滚执行** —— 所有改动先生成计划，人工确认后执行，随时整批撤销

全程离线，不上传任何文件。除视频抽帧兜底会调用本机 `ffmpeg`（可选）外，无第三方依赖。

**下载**：[官网](https://zdx8.github.io/MediaCurator-macOS/) ·
[Apple Silicon 版](https://github.com/zdx8/MediaCurator-macOS/releases/latest) ·
[通用版（Intel + Apple Silicon）](https://github.com/zdx8/MediaCurator-macOS/releases/latest)
（需要 macOS 14.0 或更高版本；首次打开若提示「无法验证开发者」，见官网的说明）

## 安全模型

照片是不可再生资产，因此工具的行为边界被刻意收窄：

| 环节 | 行为 |
|---|---|
| 扫描 | **只读**。仅读取元数据与内容指纹，不修改、不移动、不删除任何文件 |
| 生成计划 | **不碰文件系统**（只有 `fileExists` 这类只读探测），产出一份逐条可审阅的操作清单 |
| 执行 | 需要显式确认；确认页会列出所有将被移入回收站的文件 |
| 删除 | 只有**移入系统回收站**，没有不可恢复的删除路径。应用代码里不存在删除调用（`removeItem` 只出现在测试与缓存清理中） |
| 回滚 | 每次执行写入 JSONL 日志，移动/重命名原路退回，回收站文件从回收站取回 |

冲突处理默认「自动追加序号」而不是覆盖。若显式选择「覆盖同名文件」，
目标位置的原文件会**先被移入回收站**再让新文件落位，撤销时两个文件都会回到原位 ——
这条策略同样是可逆的，界面上会给出红色警告。

## 快速开始

```bash
cd MediaCurator
./Scripts/build_app.sh          # 产出 dist/MediaCurator.app
open dist/MediaCurator.app
```

出一份可分发的发布包（命名 `<app名字>-v<版本>-<机型>.zip`）：

```bash
./Scripts/package_release.sh               # → dist/影像管家-v1.0.0-arm64.zip
UNIVERSAL=1 ./Scripts/package_release.sh   # → dist/影像管家-v1.0.0-universal.zip
```

「机型」是**架构**而不是主板型号 —— Intel 机器跑不了 arm64，这个信息必须写进文件名，
否则用户下载下来才发现打不开。脚本用 `lipo -archs` 自动判定，并会把包解压到临时目录，
对**解压出来的 app** 重新跑签名校验、链接校验与两项自检。验打包前那份 .app 没有意义：
打包参数写错（例如用普通 `zip` 而不是 `ditto`，签名会被破坏）只有解包后才暴露。

> 上传到 GitHub Release 时**要把附件名换成 ASCII**（`MediaCurator-v1.0.0-机型.zip`）：
> GitHub 创建附件时会剥掉文件名里的非 ASCII 字符，中文名会被削成 `-v1.0.0-arm64.zip`
> 这种残缺样子，改名接口也救不回来。本地包名不受影响。

界面按五步工作流组织：

| 步骤 | 页面 | 做什么 |
|---|---|---|
| 1 | 扫描 | 选目录 → 读取拍摄时间、设备与内容指纹 |
| 2 | 重复项 | 逐组审阅：点缩略图放大比对，决定保留哪一份或整组都留 |
| 3 | 整理规则 | 定义目录结构与命名模板，可实时预览改名结果 |
| 4 | 执行计划 | 逐项勾选，确认后执行 |
| 5 | 操作日志 | 查看历史执行明细，一键撤销 |

### 重复项页的两种人工决定

每组卡片右上角是**保留整组**开关。它与逐个勾选的「保留」是两件不同的事：

| 操作 | 含义 | 对计划的影响 |
|---|---|---|
| 保留（缩略图下方右侧的勾选，**可多选**） | 这几份都要留下，其余算冗余 | 未勾选的成员进入待清理列表 |
| 保留整组（卡片右上角） | 这几个文件都要留，只是长得像 | 本组不产生任何清理操作 |

「保留」是复选框而不是单选按钮，因为同一组里想留几张是常见需求（连拍里挑中的两张、
同一段视频的横竖两版）。**至少会保留一份** —— 界面上不允许取消最后一个勾选，
模型层也有兜底，不会出现「整组都被判为冗余」的情况。

**「保留整组」只取消清理，不影响归档** —— 这些文件仍会按整理规则被移动到目标目录。
卡片底部的说明文字写明了这一点，否则很容易误解成整组都被跳过了。

### 放大预览

点击任意缩略图打开预览浮层：

- 图片按约 2400px 解码（`CGImageSourceCreateThumbnailAtIndex` 在解码阶段就缩放，
  比「先解全图再缩」省内存也快），支持滚轮缩放、拖拽平移、双击在适应窗口与 200% 之间切换
- 视频直接内嵌播放器（自己包装的 `AVPlayerView`，不是 SwiftUI 的 `VideoPlayer`，
  原因见「视频预览为什么会闪退」），方便比对「相似视频」组
- 方向键 `←` `→` 在组内切换，`Esc` 关闭，点空白处也关闭
- 底部显示分辨率、体积、拍摄时间及其来源、设备、完整路径
- 浮层内可直接勾选「保留」（同样支持多选），不必退出再点

窗口**右上角**是界面外观开关，点一下就在浅色与深色之间直接切换（图标显示当前状态）。
它是全局显示设置，不属于任何一步工作流，所以没有放进侧栏。

首次扫描时，macOS 会请求访问「桌面 / 文稿 / 下载」等目录的权限。

## 技术实现

### 判重为什么是三层而不是两条流水线

朴素做法是跑「精确重复」和「相似」两条独立流水线，但这会同时产生两个问题：

- **盲区**：先把字节重复挑出来、再拿剩下的做相似比对，那么「A 的缩小版」就再也找不到 A —— 明明它们是同一张照片；
- **重复上报**：两条流水线都跑全量时，同一批文件会在两个结果里各出现一次，可释放空间被重复计算。

因此实际做法是：**把「字节同一」和「视觉相似」两种边并进同一棵并查集**，最后看每个簇里含几种不同的内容标识 —— 只有一种就是精确重复，多于一种就是相似。每个概念上的「同一批素材」只产出一个分组。

### 精确重复的两级哈希

对全库逐个文件做完整 SHA-256 是纯粹的 I/O 浪费，绝大多数文件都是唯一的。所以：

1. **快速签名** —— 首 256 KB + 尾 256 KB + 文件大小，只需两次随机读；
2. 只有快速签名发生碰撞的候选组，才算**完整 SHA-256** 做最终确认。

快速签名相同是「字节相同」的必要条件（同一文件必然首尾同长），所以这个剪枝**不会漏判**。

### 相似检测的三个关键设计

**分块汉明索引**：依据鸽巢原理，若 64 位感知哈希的汉明距离 ≤ t，把它分成 t+1 块后**至少有一块完全相同**。于是只需查这 t+1 个桶的并集做候选生成，再算真实距离。常数时间、不漏判，比 BK-tree 简单得多。

**平坦画面误判**：灰度感知哈希用在纯色、天空、白墙、截图这类图上会严重碰撞 —— 两张纯色图的哈希几乎完全相同。所以额外计算 4×4 平均色网格，颜色偏差过大时拒绝合并。

**时间轴抽帧**：视频在时间轴上等距抽若干帧，各算感知哈希，比对整段序列。这样能识别「转码过 / 加了片头 / 重新剪辑过」的同一段视频 —— 字节不同、时长可能不同，但画面序列高度重合。

### 拍摄时间的读取顺序

| 来源 | 照片 | 视频 |
|---|---|---|
| 首选 | EXIF `DateTimeOriginal` → `DateTimeDigitized` → TIFF `DateTime` | ISO BMFF 的 `moov.mvhd` 头 |
| 兜底 | 文件名正则（要求「日期 + 时分秒」都完整） | `ffprobe`（MKV/AVI/MTS 等非 BMFF 容器） |
| 最后 | 文件系统创建/修改时间 | 同左 |

实现要点：

- **直接解析 `mvhd` 而不是 fork `ffprobe`** —— 一次导入可能上百个视频，每个 fork 一个进程会让规划阶段成为最大瓶颈。读文件头快两三个数量级。
- **`mvhd` 的时间基准是 1904-01-01 UTC**，不是 1970；`moov` 也可能写在文件尾部，前 512 KB 未命中时要补读尾部。
- **EXIF 时间不含时区**，按本机时区解释才与相机屏幕上显示的时间一致。
- **容器 `creation_time` 存在两种相反的设备行为**：多数相机与安卓设备把当地时间直接写进 UTC 字段，Apple 设备则严格遵守 UTC 规范。两者无法自动判别，所以界面上给了开关。
- **用 `Calendar` 而不是 `DateFormatter`** —— 后者不是线程安全的，而规划阶段会并发处理上万个文件。另外 `Calendar.date(from:)` 会把 2 月 30 日静默进位成 3 月 2 日，必须回读字段确认未发生进位。

### 界面为什么不能用 `dispatchMain()`

这是个踩过的坑，值得记下来：

`--headless` 模式最初用 `Task { } + dispatchMain()` 驱动，结果 `@MainActor` 标注和 `MainActor.run` 里的代码 **`Thread.isMainThread` 恒为 false**，`NSWindow` 创建直接抛异常；改用 `DispatchQueue.main.sync` 补救后更是彻底死锁。

根因是 `dispatchMain()` 与 Swift 并发的「主队列排空」机制不兼容。改用**主 RunLoop 泵**（`while !done { RunLoop.main.run(until:) }`）驱动后，主队列与 MainActor 都由它正常服务。`UIRenderCheck` 里保留了一条「离屏渲染在主线程上执行」的断言来守住这个前提。

### 视频预览为什么会闪退（链接期的坑）

另一个踩过的坑，这个更隐蔽 —— **它不报任何编译错误，只在你点开视频缩略图的那一刻闪退**。

现象：点重复项里的视频缩略图，进程立刻退出，stderr 里只有一行

```
failed to demangle superclass of VideoPlayerView from mangled name 'So12AVPlayerViewC': unknown error
```

根因在链接期。SwiftUI 的 `VideoPlayer` 声明在**私有框架 `_AVKit_SwiftUI`** 里，写 `import AVKit` 时编译器只会自动链接那个私有覆盖框架，**不会顺带链接 AVKit 本身**：

```bash
otool -L 产物   # 修复前只有 _AVKit_SwiftUI，没有 AVKit.framework
```

而 `VideoPlayer` 在 macOS 上内部是 `AVPlayerView`（属 AVKit）的子类，运行时找不到父类，构造即 trap。

修法是两条一起上：

1. `Package.swift` 里显式声明 `linkerSettings: [.linkedFramework("AVKit")]`；
2. 预览里的播放器不用 `VideoPlayer`，改成自己用 `NSViewRepresentable` 包一层 `AVPlayerView` —— 对 AVKit 产生真实符号引用，顺带也不再依赖那个私有框架。

防线也补了两道，因为这个缺陷在编译期完全沉默：

- **打包脚本**在签完名后校验 `otool -L` 里必须有 `AVKit.framework` 与 `AVFoundation.framework`，缺任何一个直接 `exit 1`；
- **界面自检**断言 `NSClassFromString("AVPlayerView")` 可解析 —— 这才是「AVKit 到底有没有被链进来」的直接判据。

### 一道静默失效的防线：颜色签名

用于拦「平坦画面误判」的 4×4 平均色签名，曾经在很长一段时间里**恒为全零**，而自检始终全绿。

根因是一行参数不匹配：

```swift
// ✗ noneSkipLast 是每像素 4 字节，bytesPerRow 却按 3 字节算
CGContext(data:..., bytesPerRow: side * 3, space: rgb, bitmapInfo: noneSkipLast.rawValue)
// → CGContext 直接创建失败返回 nil，函数静默返回全零缓冲区
```

（顺带说明：改用 24 位的 `CGImageAlphaInfo.none` 同样会被 CoreGraphics 拒绝。可行做法是按
4 字节/像素作图，再把 RGB 三通道抽出来紧凑存放。）

它为什么会造成实际危害？因为平坦画面的 64 位感知哈希会严重碰撞 —— 实测：

| 图片 | 亮度字节 | 64 位感知哈希 |
|---|---|---|
| 纯绿 `(30,180,60)` | 156 | `966969940596f769` |
| 近白 `(240,240,240)` | 240 | `966969940596f769` |

**两者哈希完全相同，汉明距离 0。** 没有颜色签名兜底，工具就会把一张纯绿图和一张近白图
并成一组，然后建议你「保留分辨率更高的那份，把另一份移入回收站」。

为什么原来的自检没能发现？因为那条断言是看**结果**的：

```swift
if let group = ...含 flat_blue.jpg 的分组 { 断言组里没有 flat_gray } else { check(true) }
```

而 `flat_blue` / `flat_gray` 恰好因为 JPEG 压缩噪声而没被判为相似 —— 断言通过，但**通过的理由
和它想验的东西无关**。这类「因为无关原因而通过」的测试比没有测试更危险。

修完之后，断言改成直接验防线本身，而且验的是一条能真正失败的判据：

```swift
checker.check(!签名.allSatisfy { $0 == 0 }, "颜色签名不是全零（全零意味着校验失效）")
checker.check(PerceptualHash.colorDistance(蓝, 灰) > 48, "颜色差异大时距离超过阈值")
checker.check(!DuplicateDetector.colorCompatible(纯绿图, 近白图), "哈希相同但颜色迥异时判为不兼容")
```

签名全零时第一条必定失败，颜色校验失效时后两条必定失败 —— 这条防线以后不会再静默失效。

## 验证

工具自带两个无界面自检，跑的是**实际交付的产物**（同一个二进制既能双击运行，也能被脚本驱动），而不是另编译一份测试代码。

```bash
APP=dist/MediaCurator.app/Contents/MacOS/MediaCurator

# 闭环自检：素材生成 → 扫描 → 查重 → 计划 → 执行 → 撤销 → 覆盖与回退（83 项断言）
"$APP" --headless selftest

# 界面自检：离屏渲染全部页面，校验绘图内容、页面差异、主题与配色、缩略图、视频预览（33 项断言）
"$APP" --headless uicheck --shots dist/ui-preview
```

自检素材由 ImageIO 现场合成（写入与读取走同一套键名与解码路径，不会出现「素材格式与解析预期不一致」的假通过），覆盖：

- EXIF 时间、文件名时间、视频容器时间三种时间来源
- 字节完全相同的副本、缩小一半的版本、内容完全无关的图
- **两张只有颜色不同的纯色图** —— 用来验证颜色签名确实拦住了平坦画面的误判
- 同画面不同编码的视频、画面不同的视频
- 全部媒体跨两个年份、三台设备，用于校验目录分级
- **九种目录结构模板逐条比对渲染结果**，并校验预设只用到已登记变量、
  默认模板命中某个预设（否则首次进下拉会显示「自定义」）
- **「保留整组」的四条影响面断言**：该组不再产生清理操作、归档不受影响、
  汇总的可释放空间与冗余数正确减少、分组总数不变

界面自检会导出整窗与各页的渲染图（`dist/ui-preview/`）供人工核对，
其中浅色与深色各出一张整窗总览，另有放大预览与视频预览各一张。

配色有专门的回归断言，分两层：**令牌**层精确比对 sRGB 常量（强调色与 logo 底色
都是浅蓝），**渲染**层统计画面中属于强调色族的采样点数量（证明它真的被大面积画了出来）。

> 断言里有个坑值得记一笔：渲染出的位图落在显示器自身的色彩空间（如 Color LCD），
> 而 SwiftUI 的渲染管线与 `NSColor.usingColorSpace()` 的换算结果**并不一致** ——
> 实测 sRGB `(0.21,0.53,0.80)` 经 NSColor 换算到显示器空间是 `(0.30,0.52,0.78)`，
> 画到位图里实际却是 `(0.42,0.59,0.80)`，红通道差了 0.12。
> 所以渲染层不能用精确比对，改成按色族判定（蓝 > 绿 > 红且够亮）—— 同样能区分橙、红、绿，
> 且不依赖任何色彩空间换算。

## 界面配色

代码里把**界面强调色**与**品牌色**分成两组令牌。两者当前取同一个浅蓝，但仍各自独立 ——
它们性质不同（交互反馈 vs 品牌标识），将来任一方要单独调整时不必再拆一次。
`Palette.brand` 直接引用 `Palette.accent`，所以两者不可能悄悄漂移。

| 令牌 | 取值 | 用在哪 |
|---|---|---|
| `Palette.accent` | 浅蓝 `#3687CC` | 按钮、选中态、链接、强调图标、进度条 |
| `Palette.brand` | 同强调色 | 侧栏 logo 与应用程序图标（`make_icon.swift` 用同一组数值） |
| `Palette.positive` | 深绿 `#1C6B47` | 「保留」「已就位」这类语义状态 |
| `indigo / teal / violet` | — | 分类色，只用于区分操作类型与重复类型 |

浅蓝取 `#3687CC` 而不是更浅一档，是为了白字压上去时仍有足够对比度
（约 3.8:1，与 macOS 自带强调蓝大致相当）—— 侧栏选中行和主按钮上压的都是白字。
「复制」这一项特意用青绿而不是蓝色，因为蓝色已经被强调色占用了。

> 应用图标是独立脚本生成的，引用不到 `Palette`，数值只能重复一份。
> 改配色时要**同时**改 `Components.swift` 与 `Scripts/make_icon.swift`，
> 否则 App 内 logo 与访达里的图标会不同色。

配色有专门的回归断言，分两层：**令牌**层精确比对 sRGB 分量（强调色与 logo 底色都必须是浅蓝、
且两者一致），**渲染**层统计画面中属于强调色族的采样点数量（证明它真的被大面积画了出来）。
这类断言的意义在于 —— **配色被悄悄改回去不会报任何错**，只会在某天突然发现界面变了个样。

## 已知边界

- **相机 RAW**（CR2/NEF/ARW 等）系统解码器读不了，只能读到尺寸与 EXIF，不参与相似比对，但仍参与精确重复判定。
- **跨卷移动**是真实的复制 + 删除，比同卷内的原子重命名慢得多。
- 归档计划在执行前会重新确认目标是否已被占用；若两次之间出现了同名文件，该条记为失败而不是强行处理。
- 本机 `codesign --sign -` 只是临时签名，**拷贝给别人或经网络传输后会被 Gatekeeper 拦下**。需要开发者证书签名 + 公证才能分发。本机双击运行不受影响。
